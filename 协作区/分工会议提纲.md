# EatWhat 产品组分工会议提纲

更新于 2026-10-19。主持：A。建议 30 分钟。目标：让大家知道项目做什么、自己接什么、会后怎样独立开始。姓名、日期和入口会中直接填[任务看板](./任务看板.md)，取舍写决策记录，不另建一份进度表。

## 开场可以直接这样介绍

“我们做 EatWhat，帮助一个人在工作日选择附近的一顿普通午晚餐。首页通过需求输入、地图和少量卡片完成选择，个人页管理长期偏好。我们五个人这轮负责 PRD、原型和视觉，开发由另一组安排。框架和示例已经有了，大家各补一个模块，自查后直接交我汇总，不需要相互等稿。”

接着说明这一轮的重点：

“这次先用现有原型看懂两页，再各自补用户能做的事情：从哪里开始，点了以后页面怎么变，哪些信息保留，取消或失败后怎样继续。B/C/D 交业务草图和操作规则，设计同学同时做一张首页视觉样稿与必要批注。我和设计同学明确本阶段采用的方向，再和 AI 分批合成可点击原型。我们用固定样例推进，真实 AI、地图和保存服务由开发组接入。”

## 会议顺序

| 时间 | 做什么 | 当场得到什么 |
| --- | --- | --- |
| 0–4 分钟 | 介绍用户、使用场景、两页范围与产品／开发边界 | 明确这一轮要交产品资料 |
| 4–10 分钟 | 演示首次选餐、当次反馈、偏好纠错 | 大家看到共同起点与样例限制 |
| 10–18 分钟 | 打开分工说明，认领 B/C/D；确认设计同学主责 E | 姓名、特长、可用时间登记到看板 |
| 18–24 分钟 | 用编辑偏好示范说明写多细；介绍异步与 Git 方式 | 知道四样交付物、自己的文件和任务分支 |
| 24–30 分钟 | 确定首稿时间、资料入口、A 汇总时间，收集主要问题 | 会后每人能直接开始；未定细节留书面建议 |

## A 可以照着做的 3–5 分钟演示

先说明“这是固定样例的灰度框架，用来讲结构与操作，视觉尚未定稿”。评审说明中的场景按钮会重置样例；第三条载入的是已有偏好，不演示聊天自动保存。

| 顺序 | 在原型里点什么 | 同时讲什么、交给谁补 |
| --- | --- | --- |
| 1. 首次选餐，约 2 分钟 | 选择“首次选餐” → 填入示例 → 帮我选一顿 → 补学校东门 → 应用条件 → 点地图点位／展开卡片 → 就这家 | B 补输入、补问、条件应用与取消；C 补候选、地图联动和明确选定；E 看区域主次和操作入口 |
| 2. 当次反馈，约 1 分钟 | 选择“当次反馈” → 今天不吃这类 → 换一组 → 开始新一餐 | D 补反馈对象与作用范围；C 说明换推荐保留条件；当次限制不变成长期偏好，新的用餐决策清除当次限制 |
| 3. 偏好纠错，约 1 分钟 | 选择“偏好纠错” → 在个人页编辑已有记录并取消，或确认删除 → 回首页 → 按新条件更新 | D 补原值、取消、保存／删除及结果提示；A 核对旧推荐退出；E 设计列表、控件和公共状态 |

演示完指向[分工说明](./产品组分工说明.md)的逐人任务与交稿清单，再登记姓名。讨论页面结构与下一步操作，视觉方向由 E 的首页样稿承载，首轮不要求所有画面都做完配色才交稿。

## 原型与前端交互逻辑要做到什么程度

现有[灰度原型](./原型/index.html)已有首次选餐、当次反馈、偏好纠错三条示例路径，操作范围见[原型说明](./原型/README.md)。本轮在它上面细化，保留首页与个人页两页框架。

这里的“前端逻辑”指用户能观察到的交互规则。每个关键操作在[功能需求模板](./模板/功能需求模板.md)的操作表中回答：

1. 当前处于哪张画面、什么状态？按钮什么时候可以点，缺信息时怎么继续？
2. 点下去以后，出现什么内容、提示或下一状态？
3. 哪些信息改变，哪些继续保留？当餐条件、长期偏好、未发送文字、旧推荐分别处理。
4. 需要等待时显示什么，能否再次提交？成功、无匹配和失败怎样区分？
5. 取消、返回或失败后，用户从哪里继续？是否仍保留原来的有效信息？

例如：已有 30 元预算的推荐 → 把本餐预算改为 20 元并应用 → 旧推荐不再作为当前可选结果 → 用新条件重新获取；失败时保留新条件并给出重试入口，不能把旧卡片当成符合 20 元预算的新结果。取消尚未应用的编辑，则仍使用原条件。对应 PRD 的 R-07；其他规则引用各自条目。

首轮只需把自己模块的一条正常路径和关键分支讲清，按现有模块要求交至少 3 条行为例子。等待、失败等尚未做成可点击状态的部分，可以先用编号草图或批注说明；后续补齐已列入范围的关键异常，不把“只写了批注”说成“原型已能运行”。

## 各人先完成哪一块

逐人完整要求与阶段顺序以[产品组分工说明](./产品组分工说明.md)为准，下表用于会上快速介绍。人员认领、时间和状态仍只记在任务看板，不因本表出现就算已经认领。

| 方向 | 先处理的流程 | 首轮具体成果 |
| --- | --- | --- |
| A | 三条路径的整体衔接与两页返回 | 演示共同原型；收稿后核对条件名称、临时／长期范围、旧推荐失效与保存提示，把采用内容汇入 PRD 和共享原型 |
| B | 输入需求 → 补缺失信息 → 确认条件；修改与取消 | 补 B-01／B-02 操作表和 B-S01 至 B-S04；说明缺地点、信息齐全、默认预算与当餐修改的行为 |
| C | 展示推荐 → 查看地图／卡片 → 换一组 → 明确选定 | 补 C-01／C-02 操作表和 C-S01 至 C-S04；先覆盖正常、候选不足、查看与选定的区别 |
| D | 当次反馈；个人页查看 → 编辑／取消 → 删除 | 补 D-01／D-02 操作表和对应状态草图；先写两条代表反馈及偏好纠错；长期生效未决处附建议，不能假定已经保存 |
| E | 两页导航、对话展开收起、推荐层级与公共控件 | 按 E-01／E-03 交首页样稿、个人页批注、公共状态和视觉方向；后续补完整两页视觉，业务规则沿用 PRD |

每人仍交四样：模块需求、草图／设计稿、至少 3 条行为例子、待定问题。操作表直接写在自己的模块中，不另建一份总 PRD。可点击原型是有帮助的表达方式，截图批注和编号草图也可交稿，不要求每个人先学会写前端代码。

各模块使用 PRD 第 7.1 节的固定样例独立推进。B 不等待真实定位，C 不等待 B 的最终稿，D 使用已有偏好样例，E 先用当前字段设计；跨模块缺口写假设与影响，收到后再回填。共享 HTML 仍由 A 统一整合，成员自己的草图或局部原型放各自目录，避免多人同时改同一文件。

## 日常怎样异步推进

按每人每周 4–6 小时安排，建议沿用“会后 3–5 天交首稿、A 收到后分批整合”的节奏，具体日期当场填写。学习、画图、写规则和自查都计入原有任务预算，不额外增加一套日报任务。

有实际推进时，成员在自己的工作时段结束后，发以下三项即可；不要求每天上线或即时回复：

```text
【方向／任务编号】本次补了什么：附模块、草图或 PR 链接，指出新增操作／状态。
接下来准备做什么：下一条路径或分支。
需要 A 决定什么：具体场景、自己的建议、影响谁；没有则写无。
```

A 如需每天向大家同步，只汇总三件事：已经采用的变化及入口、需要相关成员处理的具体问题、下一次交稿时间是否变化。有变化再发，避免反复重讲整个项目。正式状态由 A 回写原看板，决定回写决策记录，群消息只放摘要与链接。只需相关成员回应；确实卡住的跨模块分歧再临时讨论，未回复不能当作已同意。

你和 AI 可以这样配合：成员用 AI 补自己的局部操作表、草图和案例，自己检查后交稿；A 把稿件或 PR 链接与具体问题交给 AI，让 AI 核对与 PRD 的冲突、漏掉的返回／失败行为及受影响模块。A 确定取舍后，再整合需求和共享原型。第一轮优先把主路径与关键分支对齐，精细视觉随后持续完善。

## 什么时候可以交给开发组

以产品资料能够说明行为为标准：开发同学能从 PRD 和模块稿找到每条主路径的入口、字段含义、操作、状态变化、异常处理及对应画面；三条主路径能在原型演示，尚未演示的分支有明确编号说明。会改变主流程的未决取舍须先由 A 明确阶段方案，其余未定项与技术疑问列清建议和影响，随资料交接。

产品组说明“应该怎样表现”，开发组确定实现方式。固定样例的可点击演示不代表真实定位、推荐、保存或前端实现已经验收。

## 会前除了分工还要准备什么

- **能打开的资料：** 分工 Markdown、PRD、原型、示范和 Git 约定放在同一个私人仓库；请一位同学试开一次。离线时发完整目录，保留相对路径。
- **三分钟演示：** 预先走三条原型路径，准备首页和个人页截图作为备用。
- **共同仓库起点：** 使用已配置权限的私人仓库 lennney/eatwhat，成员接入情况与共同起点见看板。A 按[接入说明](./GitHub私人仓库接入说明.md)准备入口；请一名已接受邀请的同学验证 clone 与任务分支交稿。
- **一句完成标准：** 需求说明、草图／设计稿、至少 3 条行为例子、待定问题齐全，自己能解释操作与响应，就可交稿。

## 会末必须留下的安排

在看板填姓名、GitHub 用户名与可用时间、首稿截止、A 汇总时间、阶段版目标日期及设计文件入口。建议首稿在会后 3–5 天、A 收稿后 1–2 天汇总，实际日期按大家空闲时间定。开发产品资料接收人可登记为待指定，不阻塞本轮起稿。

Git 使用任务分支，A 统一合并；不会操作的同学让 AI 按约定执行，也可交改稿。讨论超过 3 分钟仍未解决的细节，先留下场景、建议与影响，会后异步继续。

会后 A 发一条简短通知：资料入口、大家已认领的方向、首稿日期、四样交付物及提交方式。互评和用户试用按需安排；试点、币种等未定取舍仍明确标注，不把会上展示的样例当成正式决定。

参考：[Atlassian 启动会议](https://www.atlassian.com/team-playbook/plays/project-kickoff)的目标、职责与完成标准，[GitLab 异步沟通](https://handbook.gitlab.com/handbook/communication/#asynchronous-communication)的书面协作。这里将其缩为适合五人产品组的 30 分钟会议，不引入整套流程。

2026-10-19 补充参考：[GOV.UK 原型方法](https://www.gov.uk/service-manual/design/making-prototypes)用不同精度的原型探索和表达交互；[GitLab 沟通约定](https://handbook.gitlab.com/handbook/communication/#asynchronous-communication)采用异步起步、把结论写回正式记录。这里借鉴两者，提出局部草图加操作表、按实际工作时段同步的做法；这是适配团队工时的建议，未改变任务认领或截止日期。
