# 第一次做 EatWhat 产品需求，从这里开始

更新：2026-10-20。适用于本轮五名产品成员：A 负责统筹，B/C/D 负责各自业务模块，设计专业同学主责 E。姓名、实际时间和任务状态统一在[任务看板](./任务看板.md)登记。

这轮要做的是：把已有框架补成别人读得懂的产品方案。PRD 就是说明“谁在什么情况下操作，产品应当怎样响应”。五人只负责产品内容，开发由另一组安排；不要求大家写代码、确认技术方案或跟踪开发进度。

**个人交付四样：需求说明、对应草图或设计稿、至少 3 条行为例子、待定问题。** 自己按案例检查后即可提交 A。评审、会议和用户试用为可选辅助，不是交稿门槛。

**异步优先：各自用共同样例开工、自查后提交；他人尚未交稿或没有回复，不阻止你完成自己的粗稿。** 当前 PRD 和原型就是共同起点，会议按需安排。跨模块问题写清假设和影响，由 A 集中协调。

领取任务看[逐人分工说明](./产品组分工说明.md)。把 [Git 协作约定](./Git协作约定-给AI.md)交给自己的 AI：成员在任务分支只改自己的模块与草图，在提交说明报进展，A 统一更新共享看板与决策记录。不会 Git 也可交模块改稿与图稿，由 A 汇总；交付标准相同。

## 0. 先进入仓库，把原型打开

1. **访问：**登录被邀请的 GitHub 账号，接受仓库邀请，打开 [lennney/eatwhat](https://github.com/lennney/eatwhat)。看不到仓库时，把当前登录的用户名和提示告诉 A，由 A 核对邀请；不用另建仓库。
2. **体验：**在仓库首页选择 **Code → Download ZIP**，解压完整目录，再打开 `协作区/原型/index.html`。GitHub 文件页只能看源码，不能在那里点击演示。无需安装开发环境，已 clone 的同学直接打开本地文件。下载方式参考 [GitHub 官方说明](https://docs.github.com/en/repositories/working-with-files/using-files/downloading-source-code-archives)。
3. **定位：**在任务看板找到自己的方向和任务；姓名尚未登记时向 A 报认领意向与本轮可用时间。可以先阅读 PRD、体验原型和看填写示范；不要按 GitHub 账号列表顺序推断角色。
4. **准备写稿：**不会 Git，先在下载的资料中改自己的模块；准备让 AI 做 Git 协作时，让 AI 按 Git 约定 clone 并开任务分支。下载的 ZIP 是快照，没有 Git 历史；持续协作不要靠反复下载覆盖已有改稿。

文件多时用[协作区目录](./README.md)导航。首轮只需要当前 PRD、自己模块、任务看板和模板，不必通读所有调研与历史资料。

## 1. 先花 15–20 分钟了解自己的起点

1. 本地打开[原型文件](./原型/index.html)，按[操作说明](./原型/README.md)分别走“首次选餐”“当次反馈”“偏好纠错”三条路径。评审路径在电脑右侧、手机布局下方。
2. 读 [PRD](../PRD.md)第 1、2、5、6 节，了解目标、范围、贯穿案例和共同规则，再读与你相关的页面与交接条目。
3. 在任务看板找到自己的方向，读对应模块。现有文字和原型是起草依据，仍需要你判断、补充和自查。
4. 读[填好的需求示范](./模板/需求填写示范-编辑长期偏好.md)，再用[功能需求模板](./模板/功能需求模板.md)补自己的内容。已有模块直接在原文件补，不复制出第二份主稿。

原型使用固定示例，暂未连接真实地图、AI 和存储。原型里没有的分支，可以先用草图和文字说明；不要因为点得通，就把整个需求当作已验证。

## 2. 每个人负责什么

| 方向 | 你需要回答的问题 | 从哪里开始 | 交给谁 |
| --- | --- | --- | --- |
| A 统筹 | 本轮范围是什么？模块冲突怎样取舍？怎样汇总为一份产品方案？ | PRD、待决问题与大家的改稿 | 给各模块共同规则；整合 PRD、画面和待定问题 |
| B 输入与补问 | 缺什么才问？已有信息怎样保留？默认值怎样使用和修改？ | [B 任务引导](./模块/B-输入与补问.md) | 给 C 可用的选餐条件；与 D 对齐偏好含义，给 E 交互状态 |
| C 推荐与选定 | 餐厅怎样比较？数据不足怎么办？地图查看和选定怎样区别？ | [C 任务引导](./模块/C-推荐与选定.md) | 给 D 明确的反馈对象；与 B 对齐条件变化，给 E 卡片和地图状态 |
| D 反馈与偏好 | 反馈指什么？当次还是长期？何时生效？怎样纠正记录？ | [D 任务引导](./模块/D-反馈与偏好.md) | 给 B/C 生效后的偏好变化；给 E 反馈、编辑与失败状态 |
| E 整体交互与视觉 | 信息先看哪里？两页怎样一致？状态怎样表达？ | [E 任务引导](./模块/E-交互与用户验证.md) | 给全员两页设计及公共规范；业务含义与对应负责人确认 |

每个人都负责产品判断、自己的需求和对应草图。草图可以用纸笔照片、截图批注、PPT 或熟悉的原型工具；设计稿的链接要放回模块文档。E 负责统一视觉，各模块仍需先表达清楚自己的业务。

### 不等别人，直接使用什么

直接使用 [PRD 第 7.1 节](../PRD.md)的共同样例。B 从原话和缺地点开始，C 直接假定条件已齐全并使用样例餐厅，D 使用预置长期记录和反馈对象，E 使用当前灰度两页。产品运行时有输入输出，文档设计可以同时进行。

别人的细节还没出来时，在自己的模块写：

> 临时假设：先采用当前 PRD 中的字段和操作含义。待核对对象：具体模块。影响：哪一处文案、字段或分支可能要调整。我的建议：……

接着完成其他状态、草图和案例。范围、反馈当次／长期、记录归属等产品问题交 A 汇总取舍；真实数据、存储方式、地图接入等技术疑问列入“交给开发团队的问题”，不阻止提交产品稿。没有回复不能当作假设已获确认。

## 3. 具体怎么写，写到什么程度

每个功能按下面的顺序补，篇幅以讲清楚为准。

| 要写的内容 | 你要回答的问题 | 写法例子 |
| --- | --- | --- |
| 场景与目标 | 谁遇到什么问题，完成后有什么变化？ | 用户想把“不推荐面食”改成另一个类别 |
| 入口与前提 | 从哪里进入？开始前已经有什么？ | 我的 → 某条长期偏好 → 编辑；已有原记录 |
| 输入与显示 | 哪些信息来自上一个模块，哪些显示给用户？ | 当前类别、长期范围、来源；进入时展示原值 |
| 正常操作 | 用户每一步做什么，页面如何变化？ | 点击保存 → 等待结果 → 成功后更新列表 |
| 分支与恢复 | 缺信息、失败、取消、返回时怎么办？ | 保存失败保留本次修改，允许重试；取消保留原值 |
| 与其他模块交接 | 需要谁提供什么？变化会影响谁？ | D 告诉 C 偏好已变化；首页需更新推荐 |
| 画面或状态 | 哪个草图对应哪一步？ | D-S01 列表、D-S02 编辑、D-S05 保存失败 |
| 行为例子 | 给定什么、用户做什么、应该观察到什么？ | 取消编辑后，列表仍显示原偏好 |

“字段”指显示或传递的信息项，例如预算、餐厅名称、反馈类别。先说明含义、来源、可否为空及缺失时怎样表现；接口和数据库细节留给技术设计。

一页可能包含多个状态，不必为每个状态重新画完整页面。可以在一张截图旁标注“失败时这里改成什么、保留什么、点哪个按钮继续”。编号由自己的模块维护，不需要写代码。

### 首轮：做到可以提交的产品粗稿

- 一条主路径从入口写到结束，步骤和响应能对应。
- 关键状态有草图或批注，至少能讨论正常、缺失或失败、取消或返回。
- 至少 3 条具体案例，覆盖上述不同情况；相关规则还有疑问时列出来，写自己的建议及影响。
- 区分“已有规则”“本次建议”“尚未确定”。遇到已有 Q 编号的问题直接引用；新增跨模块问题交 A 登记。
- 自己按案例走一遍，稿件足以让另一位成员复述；可先提交，后续再接收他人的异步反馈。

首轮每人主任务约 3 小时，另计自查及自主修订；这是粗稿预算。八标签全部细节和精细视觉可继续到下一轮。自愿做试用或互评的时间另按实际投入记录，安排见看板。

### 后续：把产品稿补完整并交 A 汇总

- 本轮产品范围内的正常与关键异常行为已写清，字段、文案和画面能对应。
- 采用的方案、未定问题及自己的建议分开列明；暂缓范围写清，未决部分不伪装成定稿。
- 模块涉及的共同信息写清含义，仍需 A 取舍的产品问题与开发团队回答的技术问题分开列明。
- 行为例子覆盖关键分支，有明确预期结果；它们描述产品要求，不要求本轮运行真实接口或做实现测试。

产品自查和可选试用参考见[产品自查说明](./评审与验收.md)。本组任务到产品资料提交与汇总为止，开发团队是否确认技术方案、何时开始开发，都不作为本组完成条件。

## 4. 怎样配合和提交

### 开工

把认领方向、任务编号和实际可用时间告诉 A，由 A 登记看板。先看自己的“首轮必做”，把准备交的功能和草图列出来，直接使用共同样例开工。阅读、学习、自查和修改都算投入时间，如实记录即可。

### 设计中

各自维护自己的模块，给图加编号和链接。对共享原型提出截图批注或局部修改建议，由 A/E 协调合入；同一段文件同一时间由一人编辑。没有 Git 经验可交回标明模块和版本的改稿，由 A 汇总。

需要别人提供信息时，用“具体场景＋暂用假设＋缺什么＋自己的建议”留言，继续完成其他内容。例如：

> 我在设计 C-02 换推荐。先按当前原型的“应用条件”作为提交点，预算从 30 改为 20 后，旧卡片退出当前可选结果，重新获取后显示。待 B 补充是否更改提交控件；E 可据此先画等待状态。我继续完成候选不足与选定路径。

能在模块内解决的文案和控件由主责推进。跨模块语义、范围和优先级由 A 协调；形成的决定进入决策记录，相关负责人再更新自己的需求。

### 交稿

自查后把成果链接和下面的交稿说明交 A，由 A 更新看板；有空的成员可以异步评论，不必先等指定评审人。

使用 Git 时，把自己的任务分支推送到仓库，并向 main 创建 Pull request（PR，即合入申请），沿用仓库里的填写模板；由 A 整合到主干。不要把“分支已提交”当作“已合入 main”。不会 Git 时，交标明任务编号与版本日期的模块改稿、图稿或批注，A 负责合入。具体 Git 操作可以交给 AI，但先告诉它是否要完成远端交稿。

```text
我负责：任务编号／功能编号
这轮补了：具体功能和状态
需求与草图：链接、画面编号
请重点看：一个具体疑问或衔接点
仍需决定：问题、我的建议、影响谁
实际投入：小时数
```

想给反馈的同学可以指出“哪一步不清楚、可能导致什么、建议怎样改”。主责在自己的工作时段处理；没有反馈也可提交。看板只记录待认领、进行中、已提交、已汇总，不安排必须通过的互评环节。

### 分批整合与分时试用

A 按已收到的成果分批整合，处理产品语义和范围问题，以文字记录采用内容和未定项；成员按记录回填自己的部分。其他人未交稿时，已完成的模块可继续完善说明或视觉。共同会议只在有需要时安排。

有余力时，可选用 A 准备的任务和记录方式，各自在方便的时间观察一名参与者或阅读已有记录，无需全员同时在线。E 分析交互与视觉问题，B/C/D 修自己的业务问题。实际结果写在同一份记录中；试用没开展时留空，不影响产品稿提交。

## 5. 怎样使用 AI

先给 AI 当前规则和自己模块，再让它辅助补局部内容。可以直接使用：

```text
我是 EatWhat 的【B/C/D/E】负责人，本次处理【任务编号】。
先读 AGENTS.md、README、协作区/Git协作约定-给AI.md、PRD 相关条目、我的模块及任务看板。
先检查实际目录、分支和已有改动，保留他人的成果。
按“新成员开始这里”的首轮标准，帮我梳理本任务。
先说明已有规则、我需要判断的问题以及建议，再协助写操作表和行为例子。
新增取舍标为提案，资料缺失写明；不编造用户访谈或测试结果。
只修改我的模块和自己的图稿；不直接改 PRD、共享看板、决策记录和共享原型。
跨模块问题列出影响，交 A 协调；任务进度与成果链接随稿交 A，由 A 更新看板。
缺少其他成员的稿件时，先用 PRD 第 7.1 节共同样例并注明假设，完成独立部分，不等待回复。
按当前有效授权完成局部编辑、检查和 Git 交付，最后说明改了什么、如何检查、还缺谁提供什么，以及是否已推送或合入。
```

使用 AI 后，自己拿着三条案例走一遍，能解释为什么这样设计。AI 可以帮助发现遗漏，最终交付的判断需要本人理解并认可。

## 6. 常见问题

**我不会画原型怎么办？** 先截取现有页面，圈出入口和变化，旁边写操作与响应。E 同时可按当前原型和 PRD 设计，收到你的说明后再回填细节。

**原型已经做了，我还要做什么？** 核对它是否符合规则，补缺少的分支和条件，解释设计选择，提出具体改进和验收案例。当前样例没有替你做完完整业务设计。

**不知道失败怎么处理怎么办？** 先写“失败后哪些内容要保留、用户下一步能做什么”，画出提示和继续入口。表现疑问交 E，技术疑问另列给开发团队，不等待确认才交稿。

**写到多长才够？** 让读者能按步骤操作和判断结果即可。“支持编辑”“优化体验”还不够；具体触发、响应、失败恢复和例子更有用。

**第一次没写完整怎么办？** 首轮交粗稿和问题清单，后续在自己的工作时段补充。不要把不确定的内容写成已确认规则。
