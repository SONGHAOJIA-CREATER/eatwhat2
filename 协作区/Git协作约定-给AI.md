# EatWhat 产品组 Git 协作约定

主要读者：协助 A/B/C/D/E 做产品资料的 AI。人类成员只需给出自己的方向、任务和交付要求。先读根目录 [AGENTS.md](../AGENTS.md)、[README](../README.md)、[分工说明](./产品组分工说明.md)、PRD 相关条目及模块稿。私人仓库接入看[GitHub 说明](./GitHub私人仓库接入说明.md)。本约定不授权向远端发布，也不把产品任务扩大为开发。

## 1 先检查实际工作区

每次开始先运行只读检查，报告目录、分支、已有改动与本轮文件范围：

```powershell
git rev-parse --show-toplevel
git branch --show-current
git status --short
git diff --name-only
git diff --cached --name-only
git log -3 --oneline
git remote
```

当前 main 为产品资料整合分支，已配置 origin。2026-10-18 已设置私人仓库和仅所有者更新 main 的规则；成员在任务分支工作，实际接入与共同起点见看板。后续 AI 必须重查工作区，不沿用初始化前的脏改动快照。未跟踪文件不会随提交自动出现在别人 clone 的目录或新 worktree 中。

若遇到 dubious ownership，先核对所有者和路径，只对已确认的单次命令使用精确 safe.directory；不要全局信任所有路径。不要输出凭据或含令牌的远端地址。

## 2 A 先准备共同起点

A 更新共同资料时遵守：

1. A 核对哪些产品资料适合团队访问，不改变仓库可见性。原始聊天和旧开发计划保留在本地，不重新纳入当前产品资料树；已有历史保持原样。
2. 按明确文件清单整理当前 PRD、README、AGENTS.md、协作说明、模块、必要参考和原型。检查相对链接可达；不把 output、临时截图或全部未跟踪内容顺手加入。
3. 按当时用户授权完成本地提交；已有明确远端同步授权时再同步 main。记录共同起点提交号，确认成员能获取资料。
4. 分支从该起点创建。共同起点尚未同步时，可先分发保留目录结构的资料；AI 不宣称多人 Git 协作已就绪。

2026-10-18 已核实远端为私人仓库 lennney/eatwhat，所有者 lennney，默认分支 main。规则 product-main-owner-only（25347151）仅允许 lennney 例外更新 main；成员不能推送或自行合并到 main。邀请和接受状态以看板为准；执行时重新核对。output/pdf、tmp、旧开发计划及本地背景资料已忽略，原型检查记录与截图按明确清单保留。

## 3 一人一任务分支和修改范围

main 用于 A 整合；成员在自己的 clone 中开任务分支，不直接在 main 写稿。首轮建议一人一个分支覆盖本模块两项相关任务，后续新一轮另开分支。

| 角色 | 分支例子 | 默认允许修改 |
| --- | --- | --- |
| A | codex/prd-a-integration-r1 | 本轮明确涉及的 PRD、共享索引、看板、决策、说明；统一原型需同时维护源与导出 |
| B | codex/prd-b-input-r1 | 协作区/模块/B-输入与补问.md、自建的 B 草图 |
| C | codex/prd-c-recommend-r1 | 协作区/模块/C-推荐与选定.md、自建的 C 草图 |
| D | codex/prd-d-preferences-r1 | 协作区/模块/D-反馈与偏好.md、自建的 D 草图 |
| E | codex/prd-e-design-r1 | 协作区/模块/E-交互与用户验证.md、自建的 E 设计稿与规范 |

本地图片可放 `协作区/原型/模块草图/B/` 等各自目录，按需新建；使用在线设计文件时把链接放回自己的模块。B/C/D 不直接改共享 HTML；E 默认交视觉稿，改共享 HTML 须在本任务范围中明确。不要新增另一份总 PRD。

Git 模式由 A 在 main 维护共享看板、决策记录和原型源。成员把进展、候选决定、变更影响写在本模块及提交说明，A 汇总时更新公共记录；不要为抢更新看板而互相等待。

## 4 开分支并完成局部修改

以下命令以 B 为例。只有共同起点已同步、当前目录没有他人未提交工作且当前任务分支不存在时，才执行：

```powershell
git fetch origin
git switch -c codex/prd-b-input-r1 origin/main
```

若任务分支已存在，先检查它是否属于当前任务，再继续使用，不覆盖重建。若当前有别人的脏改动，不为切分支而 reset、restore 或自动 stash。多人用不同机器时各自 clone 即可；同一机器多个 AI 需要并行时，可按已授权范围使用不同 worktree，或顺序执行，不能在同一目录同时切分支。

可选 worktree 示例：先核对路径未被占用、分支不存在，且 origin/main 已有共同起点，然后执行 `git worktree add -b codex/prd-b-input-r1 ../eatwhat-prd-b origin/main`。之后所有读写与 Git 命令都使用返回的工作目录；worktree 不会复制主目录的未提交资料。不要为了套用示例擅自创建或删除其他人的工作目录。

起草用 PRD 第 7.1 节固定样例；新取舍标为提案。缺其他模块内容时注明假设继续完成局部需求，不扩大到整站重构、后端、模型或算法。

## 5 检查和提交

先核对实际 diff 和未跟踪文件；新文件先阅读完整内容，尚未暂存时不会出现在普通 git diff 中。提交权限以当前任务和有效授权为准。允许提交时逐个添加本任务文件，示例：

```powershell
git diff -- "协作区/模块/B-输入与补问.md"
git diff --check
git add -- "协作区/模块/B-输入与补问.md"
git diff --cached --check
git diff --cached --stat
git diff --cached
git commit -m "docs(B): clarify onboarding and meal conditions"
```

新草图也要按实际路径逐个添加。不能用 `git add .` 或 `git add -A` 把别人的内容带入；已有暂存内容不属于本任务时，不直接提交整个暂存区，应先报告并使用独立工作目录完成本任务，不擅自替他人取消暂存。

检查内容：本模块的链接、需求／画面编号、正常和关键分支是否对应，至少 3 条行为例子是否有明确预期。纯文档任务不安装应用依赖，也不运行无关开发测试。若授权修改共享原型，运行现有 `export.cjs`，检查本次受影响的操作并保持源与导出对应。

### 图稿与需求怎样对应

本地草图放在各自的模块目录，例如 `协作区/原型/模块草图/B/`，文件名使用画面编号，例如 `B-S01.png`；模块文档引用对应文件，并和需求一起提交。不另建一份图稿状态看板。

使用在线设计文件时，在本模块和交稿说明写出入口、对应画面编号及本次交付的版本／日期，确认团队能查看。随本次交稿附关键画面的 PNG 或 PDF 快照，放在自己的草图目录并链接；可以用一份文件包含多张画面，不要求每个状态单独导出。后续修改时同步更新快照与模块说明，Git 历史保留交稿时的画面依据。

## 6 怎样交给 A 和合并

本地分支、提交号和成果链接即可说明已做什么；提交到远端需当前用户已授权。需要远端分支时，使用当前实际任务分支，例如 `git push -u origin codex/prd-b-input-r1`。不主动推 main、强推、改权限或邀请成员。

建议通过 PR 交稿，不设成员互评或批准门槛。main 已限制为所有者 lennney 更新，成员 AI 不尝试直接推送或自行合并到 main，不修改或移除规则。没有 PR 时也可以交任务分支和提交号，由 A 整合。创建 PR 后按当前工具规则附到本任务。

A 合并时先看该分支相对 main 的文件清单、具体 diff 和未定项；只整合本轮产品成果，不以合并表示所有提案均已确认。按已有授权将任务分支 merge 到干净的整合目录；有语义冲突时保留双方意图，A 作取舍后同步 PRD 与模块，不用整文件 ours/theirs 覆盖。

新手默认不要求 rebase；分支落后但无冲突时可由 A 直接整合。若产品规则已变化，只补实际受影响的部分。合入后 A 更新看板；成员下一轮从最新共同起点开新分支。不自动删分支或 worktree。

## 7 AI 交付格式和任务提示

交付时说明：角色与任务编号、工作目录／分支、修改文件、需求与画面、检查结果、未定问题与影响、提交号、是否已推送／合入，以及成员实际填报的时间。没有执行的推送、检查、访谈与人工投入不写成完成。

可以直接把下面这段给 AI，替换角色和任务，按实际目标说明是否需要提交或远端交付：

```text
我是 EatWhat 产品 B，负责 T-B01、T-B02。
先读 AGENTS.md、README、Git 协作约定、PRD 相关条目、B 模块和任务看板。
先检查实际目录、分支、暂存及未跟踪内容，沿用已有授权，不覆盖他人工作。
本轮交付：B 模块需求、B-S01 至 B-S04 草图或状态说明、至少 3 条行为例子和待定问题。
只修改 B 模块及 B 自己的草图；不改 PRD、共享看板、决策记录和共享 HTML。
直接使用共同样例，不等 C/D/E；新增取舍标提案，技术疑问另列。
按当前授权完成局部编辑、检查与 Git 交付；未获远端授权时保留本地成果。
最后报告文件、分支、检查、未定项及实际 Git 状态，由 A 统一整合。
```
