## 各方向的模块主稿

- A：[PRD 产品主稿](../PRD.md)，负责整体框架和整合。
- B：[输入与补问](./模块/B-输入与补问.md)。
- C：[推荐与选定](./模块/C-推荐与选定.md)。
- D：[反馈与偏好](./模块/D-反馈与偏好.md)。
- E：[整体交互与视觉](./模块/E-交互与用户验证.md)。

每个模块开头都有“独立起点、首轮必做、后续补齐、画面与交付”。先在原文件补，不再创建第二份总 PRD。自己新建的图稿放 `原型/模块草图/B/` 等对应目录，按需创建；在线设计文件在本模块附链接、版本与关键画面快照。

| [既有业务规则与调研依据](./既有业务规则与调研依据.md) | 追溯详细原规则、同类项目与研究来源 |

遇到不一致，先在本模块写清具体场景、暂用假设、建议和影响，交 A 协调。原型能点击不等于规则已确认；模块被合入也不等于所有提案都被采用。

## 资料怎样保持一致

- **产品要求：**PRD 是整合主稿，B 至 E 模块保留细化与依据；A 将采用内容汇入 PRD 或精确引用。
- **任务状态：**只在任务看板维护，由成员报告、A 更新；不再要求成员另填日报或另一套任务系统。
- **设计决定：**结论和待决项在决策记录维护，成员不能把自己的建议写成团队已确认。
- **原型：**`原型/eatwhat-flow.fragment.html` 是源文件，`原型/index.html` 是预览导出，由 A 统一整合；具体维护说明见原型目录。
- **分享文件：**PDF 和截图是有日期的快照，阅读当前需求仍回到 Markdown 主稿。早期七人实施方案与原始聊天留在 A 本地，当前目录只管理产品组资料。
