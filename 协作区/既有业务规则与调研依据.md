# EatWhat 既有业务规则与调研依据

整理日期：2026-10-15。

当前产品框架与模块交接见 [PRD 主稿](../PRD.md)。本文件保留原 PRD 第 1 至 15 节的业务共识，以及第 19.3、19.4 节的研究来源，原文和原编号保持不变，供按需查阅。算法、记忆提取和排序细节不属于本轮 A 的新增设计任务。

原第 12.2 节的“最近一次临时状态”须结合第 8、13 节的仅当次原则理解；原有表述一致性由 Q-11 跟进。任何新的取舍仍按[决策记录](./决策记录.md)维护，不因整理为参考文档而改变确认状态。

## 1. 产品定义

EatWhat 是一个帮助用户解决“现在吃什么”的决策型产品。

它的核心不是提供更多餐厅信息，也不是做地图浏览，而是帮助用户在当下更快做决定，并且更少后悔。

当前已经确认的产品承诺是：

**不是帮用户找最热门的店，而是帮用户少选错。**

## 2. 第一版核心用户

第一版核心用户是：

**经常纠结“吃什么”的人。**

这里的重点不是职业身份，而是用户存在高频吃饭决策纠结。

## 3. 第一版主场景

第一版主场景已经确认如下：

**工作日，一个人，在当前位置附近，想尽快决定一顿普通午餐或晚餐。**

这意味着第一版先聚焦日常、高频、低决策时长场景，不先扩展到复杂聚餐、旅行、深度探索等场景。

## 4. 第一版输入方式

第一版产品形式为网页，原型和交互优先适配手机屏幕（2026-10-13 确认）。

第一版输入方式已经确认如下：

**用户先说一句话，然后系统只在必要时补问少量问题。**

产品不应一开始就让用户填写复杂表单。

## 5. 每次决策的输入分级

第一版按以下规则处理决策输入：

- 当前位置是阻断字段。系统没有可用位置时必须询问。
- 一个人吃还是和别人吃是决策字段。缺失时需要询问。
- 预算范围是决策字段。系统可以使用用户确认过的日常默认值，否则需要询问。
- 明显约束 / 不想吃什么是可选字段。用户没有表达限制时，系统不强迫用户提供。

系统只询问会改变候选集或前三名结果的信息。系统使用历史默认值时，需要展示对应假设并允许用户修改。

## 6. 第一版推荐结果形式

第一版默认返回 3 个推荐结果，不做长列表。

这 3 个推荐结果的角色已经确认如下：

- 最稳妥
- 轻探索
- 低风险兜底

也就是说，系统不是简单返回 Top 3，而是返回 3 种不同决策角色的推荐。

## 7. 第一版反馈方式

第一版采用标签化反馈，不采用只有点赞/点踩的极简反馈方式。

当前已经确认的第一版必备反馈标签如下：

- 太远
- 太贵
- 太油
- 不想排队
- 今天不想吃这个
- 这类以后别推荐
- 这家符合我
- 这家踩雷了

## 8. 第一版记忆规则

当前已经确认的记忆规则如下。

### 8.1 长期记忆

以下标签应进入长期记忆：

- 太远
- 太贵
- 太油
- 不想排队
- 这类以后别推荐
- 这家符合我
- 这家踩雷了

### 8.2 当次记忆

以下标签只记当次，不进入长期偏好：

- 今天不想吃这个

这条规则的目的是避免把用户的临时状态误记成长期偏好。

## 9. 第一版排序优先级

当前已经确认的第一版排序优先级如下：

1. 先排除明显不合适的
2. 再看当前场景是否匹配
3. 再看距离和预算
4. 最后再看口味偏好和轻探索

这意味着第一版产品哲学已经明确为：

**先少犯错，再追求惊喜。**

## 10. Agent 的职责边界

当前已经确认，第一版采用：

**算法优先，Agent 辅助。**

第一版中，Agent 只在以下 3 种情况出手：

- 用户一句话信息不完整，需要补问
- 排序结果出来后，需要把原因解释成人话
- 用户给了自由文本反馈，需要转成结构化标签

一句用户表达可以包含一个主意图和多个次要意图。主意图决定本轮主要响应，业务规则按固定顺序处理次要意图。默认顺序是：先完成用户可见的主要动作，再记录反馈事件，最后校验并更新长期记忆。模型不能决定副作用顺序，也不能绕过记忆写入规则。

除此之外，默认应优先使用算法和规则，不让 Agent 驱动整个推荐主链路。

## 11. 当前已确认的产品原则

截至目前，我们已经共同确认了这些原则：

1. 这是一个解决“现在吃什么”的决策产品，不是内容平台。
2. 第一版服务的是高频纠结吃什么的人。
3. 第一版先打工作日、一个人、附近、普通午晚餐场景。
4. 第一版输入方式是一句话进入，必要时再少量补问。
5. 当前位置是阻断字段；同行人数和预算按输入及已确认默认值决定是否补问；明显约束是可选字段。
6. 第一版默认给 3 个推荐，而且 3 个推荐有固定角色分工。
7. 第一版反馈采用标签化方式。
8. 第一版记忆明确区分长期与当次。
9. 第一版排序先保证少犯错，再考虑偏好和探索。
10. 第一版主链路算法优先，Agent 只做高价值辅助。

## 12. 已确认的排序服务设计

### 12.1 排序服务输入

第一版排序服务除了接收当次决策必需信息之外，还应显式接收：

- 历史反馈摘要
- 标准化的候选餐厅基础属性

### 12.2 历史反馈摘要内容

第一版历史反馈摘要最少包含以下 4 类：

- 长期负向约束汇总
- 正向确认过的偏好汇总
- 明确拉黑的类别或餐厅
- 最近一次临时状态

### 12.3 候选餐厅基础属性

第一版排序服务应接收标准化的候选餐厅基础属性，当前已确认的最小集合为：

- 距离
- 价格带
- 餐厅类别 / 菜系
- 基础位置标识
- 是否命中过去有反馈的店或类型

### 12.4 排序服务输出

第一版排序服务不能是黑盒。

除了最终排序结果之外，还必须输出可追踪的结构化原因，至少包括：

- 命中了哪些约束
- 触发了哪些扣分项
- 为什么被分配成某个推荐角色
- 是否命中了历史正反馈或负反馈

### 12.5 排序分数结构

第一版排序先拆成 4 个大维度分，再汇总总分：

- 约束满足分
- 场景匹配分
- 成本分
- 偏好 / 探索分

### 12.6 成本分定义

第一版成本分先只包含两项：

- 距离
- 预算

### 12.7 场景匹配分定义

第一版场景匹配分先只看两个因素：

- 是否一个人吃
- 是否工作日普通午晚餐

其中用餐时间默认由系统按当前时间自动判断，不优先让用户手动选择。

### 12.8 约束满足分定义

第一版约束满足分当前只由以下 4 个长期约束驱动：

- 太远
- 太贵
- 太油
- 不想排队

### 12.9 偏好 / 探索分定义

第一版偏好 / 探索分先只看两类内容：

- 用户明确正向确认过的偏好
- 在不违反长期负向约束前提下提供一点轻微新鲜感

### 12.10 三类推荐角色定义

第一版 3 个推荐角色当前定义如下：

- 最稳妥：综合分最高，且最符合当前约束和场景
- 轻探索：不违反用户长期负向约束，在安全范围内提供一点新鲜感
- 低风险兜底：近、便宜、容易决定

### 12.11 正向反馈处理

第一版“这家符合我”先作为简单正向信号处理：

- 给这家店加分
- 给这类店适度加分

第一版不把这条反馈直接扩展成复杂深层偏好学习。

### 12.12 负向反馈处理

第一版“这家踩雷了”按两层处理：

- 这家店强负向
- 这类店弱负向，后续可被新的正向反馈修正

第一版“这类以后别推荐”定义为强长期负向，强度高于“这家踩雷了”。

## 13. 已确认的记忆系统分层

### 13.1 两套记忆系统

第一版记忆系统当前确认分为两套：

- 聊天内容记忆系统
- 饮食记忆系统

### 13.2 聊天内容记忆系统

聊天内容记忆系统用于服务当前这次对话，属于短期记忆。

它的职责是：

- 保留当前会话中的上下文
- 支撑当前轮追问和理解
- 承接用户在本次会话中的自由表达

### 13.3 饮食记忆系统

饮食记忆系统用于沉淀长期可复用的饮食相关偏好和约束。

它的职责是：

- 为后续排序服务提供长期记忆输入
- 沉淀结构化的约束、偏好、踩雷和正向反馈
- 让下一次推荐体现“越用越懂你”

### 13.4 两套记忆的关系

当前确认的关系如下：

- 用户在一次聊天中的表达，先进入聊天内容记忆系统
- 一次聊天结束后，系统自动从本次聊天和反馈中提取可沉淀信息
- 可沉淀的信息再写入饮食记忆系统
- 下一次推荐时，排序服务主要依赖饮食记忆系统，而不是直接依赖完整聊天历史

### 13.5 允许进入饮食记忆系统的内容

第一版当前确认，以下 3 类内容允许从聊天内容记忆进入饮食记忆系统：

- 用户明确表达的长期约束
- 用户明确给出的结构化标签反馈
- 用户对某类店或某家店的明确正负判断

### 13.6 不应直接进入饮食记忆系统的内容

第一版当前确认，以下内容不应直接长期化：

- 模糊表达
- 临时情绪化表达
- 与饮食决策无关的闲聊内容
- 仅服务当前轮对话、但没有长期意义的信息

### 13.7 聊天结束后的提取时机

第一版一次聊天的结束判定先采用简单规则。

满足以下任一情况，就触发从聊天内容记忆到饮食记忆系统的提取：

- 用户选了某个推荐
- 用户给出反馈后不再继续换推荐
- 用户明确表示“就这个”“先这样”“不用再推了”

### 13.8 饮食记忆的置信度

第一版写入饮食记忆时，记忆项应带有置信度字段。

### 13.9 置信度生成方式

第一版置信度先采用简单规则生成，不使用复杂学习模型。

当前确认可作为置信度规则输入的信号包括：

- 用户是否明确表达
- 是否重复出现
- 是否有标签反馈佐证
- 是餐厅级判断还是类别级判断

### 13.10 不同反馈的置信度起点

第一版当前确认的置信度起点规则如下：

- “这类以后别推荐”默认给最高置信度起点
- “这家踩雷了”默认给中高置信度起点
- “这家符合我”默认给中等置信度起点
- “太远 / 太贵 / 太油 / 不想排队”这类约束反馈默认给中高置信度起点
- “今天不想吃这个”不进入长期饮食记忆置信度体系，只在当前会话和本次决策里生效

## 14. 已确认的推荐理由展示方式

### 14.1 第一版展示原则

第一版推荐理由服务于“快速做决定”，不服务于长篇阅读。

因此默认不展示长段解释，而采用轻量、可扫读的形式。

### 14.2 推荐卡片理由结构

第一版每张推荐卡默认展示：

- 1 句主理由
- 2 个结构化标签

### 14.3 主理由要求

主理由应优先基于排序服务输出的结构化原因生成。

主理由应尽量回答：

- 为什么这家店适合你现在

主理由不应写成长段文案，也不应包含无证据的扩展描述。

### 14.4 结构化标签要求

第一版结构化标签优先展示最有决策价值的信息，例如：

- 近
- 预算合适
- 一个人吃更合适
- 命中过往正向反馈
- 避开了太油
- 避开了排队风险

### 14.5 默认交互

第一版推荐卡默认只展示轻量理由。

如需更详细说明，可在后续版本中再提供“展开查看更多原因”的交互，但这不是第一版必须能力。

## 15. 已确认的排序权重优先级

### 15.1 第一版权重原则

第一版排序权重已经确认采用以下优先级：

1. 约束满足分最高
2. 场景匹配分第二
3. 成本分第三
4. 偏好 / 探索分最低

这意味着第一版排序的核心目标明确为：

**先减少错误选择，再提升个性化和探索感。**

### 15.2 第一版权重表达方式

第一版当前先确认权重优先级，不急着在 PRD 中锁死具体数值。

后续进入实现设计时，再结合你现有记忆系统、候选数据质量和测试结果，补具体权重草案。
