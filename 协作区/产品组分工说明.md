# EatWhat 产品组分工说明

更新于 2026-10-19。适用：本轮五名产品成员。A 负责统筹，B/C/D 按兴趣与特长认领，设计专业同学主责 E。姓名、账号与方向的对应关系、日期和进度只在[任务看板](./任务看板.md)登记，不按账号提供顺序分配。

## 我们这轮要完成什么

EatWhat 帮助一个人在工作日选择附近的一顿普通午餐或晚餐。用户说清本次需要，补充地点，比较少量推荐，选定或反馈；个人页用于查看、修改和删除长期偏好。

当前工作方案是两页：**首页放地图、推荐卡片和对话辅助；个人页管理默认值与长期偏好。** 算法、地图接入、存储和开发排期由开发组另行安排。本组交付能讲清操作与响应的 PRD、原型和视觉稿。

| 方向 | 负责哪一块 | 对应任务 | 本轮交给 A 什么 |
| --- | --- | --- | --- |
| A 统筹 | 范围、两页框架、跨模块取舍、整合 | T-A01 至 T-A03、T-E02 | 一份整合 PRD、画面索引和未定问题 |
| B 输入 | 引导、补问、默认值、修改条件 | T-B01、T-B02 | 输入规则、4 个关键状态、行为例子 |
| C 推荐 | 卡片、地图关系、换推荐、选定 | T-C01、T-C02 | 卡片字段、4 个关键状态、行为例子 |
| D 偏好 | 反馈语义、个人页、编辑与删除 | T-D01、T-D02 | 反馈规则表、管理流程、状态与例子 |
| E 设计 | 整体交互、视觉方向、公共规范 | T-E01、T-E03 | 首页样稿、个人页批注、公共样式与检查场景 |

## 先演示，再怎样一起做

本轮按下面的顺序推进。**B/C/D 的业务草图与 E 的视觉样稿同时做，A 分批整合。** 首轮交粗稿，后续补关键异常和完整视觉；不用等所有颜色或文案定稿才开始写交互。

| 阶段 | 谁做、具体怎么做 | 这一阶段得到什么 |
| --- | --- | --- |
| 1. 共同看框架 | A 用现有灰度原型演示 3–5 分钟，讲首次选餐、当次反馈、偏好纠错；大家标出不清楚的地方 | 知道两页分别解决什么、主操作在哪里、自己的模块从哪里开始；具体脚本见[会议提纲](./分工会议提纲.md) |
| 2. 各自补细节 | B/C/D 用截图批注或简单草图表达业务状态，补操作表和例子；E 同时按共同样例做一张推荐状态首页视觉样稿 | 各模块的关键状态草图与交互规则，外加一张可讨论视觉方向的首页样稿；这批成果即可提交 A |
| 3. 采用并回填 | A 处理跨模块取舍，与 E 用书面说明确定本阶段采用的视觉方向及待改项；E 将采用方向扩展到个人页和公共控件，各模块按实际影响回填 | 采用内容与待定项有明确记录；视觉结论由 A 记入决策记录，不把未回复当作同意。这个步骤不阻塞其他模块交粗稿 |
| 4. 合成并交接 | A 和 AI 把收到的业务规则与采用的视觉方案逐项应用到共享 HTML 原型，检查本次受影响操作，再同步 PRD 与画面引用 | 三条主路径可演示，关键分支有画面或编号说明；开发组据此确定实现方式 |

这里有三种不同成果：**业务草图**说明区域、入口和状态变化；**视觉样稿**说明布局、层级、颜色、字体和控件外观；**可点击原型**把操作串起来。它们可以逐步完善，不要求每个人把同一张页面重复画成高保真。

A 尚未反馈视觉方向时，E 可以继续个人页草图、公共控件和已有方向下的局部状态，标明尚未采用；不必停下等回复，也不同时精修多套配色。其他模块继续沿用共同样例，收到采用结论后只改受影响部分。

继续使用现有 HTML 原型和固定样例。B/C/D 可交截图批注、纸笔图或局部可点击稿；E 用熟悉的设计工具交样稿和规范。A 负责与 AI 修改共享源文件并导出预览，成员不必为这轮任务统一学习一套前端框架。真实 AI、地图和保存服务接入由开发组负责，原型演示使用的样例要明确标注。

## 所有人先看这三样

1. 用 5 分钟体验[当前原型](./原型/index.html)的首次选餐、当次反馈、偏好纠错三条路径。原型使用固定示例，没有真实 AI、地图或保存服务。
2. 读 [PRD](../PRD.md)第 1、2、5、6、7.1 节，了解范围、贯穿案例、共同规则和各自可直接使用的样例。
3. 读自己的模块和[填写示范](./模板/需求填写示范-编辑长期偏好.md)。已有内容是起点，接下来要补具体步骤、分支和画面。

以下每个方向一节，可直接找到自己的任务。第一轮每人约 4 小时：主任务 3 小时（含阅读），自查 0.5 小时，自主修订 0.5 小时；这是粗稿预算，日期由本次会议确定。

## 全员沿用的边界

- 没有有效位置，先补地点；不猜一个城市来推荐附近餐厅。
- 今天的限制与长期偏好分开；选定一家店不等于吃过或满意。
- 未知价格、距离等信息明确写未知；不为了凑三家编造餐厅。
- 各自用共同样例开工，不等其他人交稿；未定项写假设、建议和影响。
- 自查后直接提交 A，互评和用户试用可选；开发确认不是本组交稿条件。

## 每个操作都要写清楚什么

在自己的模块主稿中按[功能需求模板](./模板/功能需求模板.md)填写，和自己的画面编号对应：

| 必须说明 | 要写到的程度 |
| --- | --- |
| 入口与当前状态 | 从哪一页、哪个按钮进入，已有条件或记录是什么 |
| 可操作条件 | 按钮什么时候可以点，缺信息时怎样补充，等待时能否重复提交 |
| 操作后的变化 | 出现哪张画面、哪条提示或哪个下一状态；不只写“调用接口” |
| 信息保留与生效 | 哪些条件、原值、草稿和记录保留或改变；旧推荐是否还能选 |
| 取消与恢复 | 取消、返回、失败和重试后，用户看到什么、下一步能做什么 |

例如“编辑偏好”要说明：进入时看到原值；取消后原记录不变；保存成功后显示新值；失败时保留本次修改、提示未保存并允许重试。保存中、成功和失败可以先在草图旁写状态批注，不必每个状态画一整页。

**首轮交稿标准：自己的正常路径和关键分支能够讲通，需求、图和至少 3 条例子能互相对应，未定问题附建议和影响。** 后续要补齐的内容按各节说明列出，不把批注或样例当成已经实现的真实能力。

## B 输入与补问

**目标：让用户以少量操作说清这一顿需要什么，知道缺什么，并能修改。** 正式需求写在 [B 模块](./模块/B-输入与补问.md)。

### 先看什么

走原型的“首次选餐”；读 PRD 第 3.1、4 节及 R-01、R-02、R-07、R-08，再看 B 模块开头。不要从零重写整个项目 PRD。

### 具体补什么

按下面顺序动手：先列输入项和缺失情况，再画首次输入／补地点，随后补条件确认与修改，最后逐行填写操作表。先用灰度图表达，视觉沿用现有占位，采用 E 的公共样式后再由 A 整合。

1. 首次进入介绍什么，哪里输入，偏好引导怎样跳过；跳过后仍能选餐。
2. 已说清人数、预算和限制但缺地点时，怎样补地点，怎样保留已有信息。
3. 条件齐全时怎样显示摘要、进入推荐；用了默认预算时怎样看见和修改。
4. 修改地点或预算时的应用、取消、返回，以及旧推荐怎样退出当前结果。

独立样例：“一个人，30 元以内，今天不想吃面”，尚无地点、无默认预算。另设“学校东门，一个人，30 元以内”的条件齐全样例。两者都可直接设计，不等 C/D。

### 画哪些原型

| 编号 | 首轮必须表达的内容 |
| --- | --- |
| B-S01 首次输入 | 简短用途、输入框、例句、跳过偏好入口 |
| B-S02 缺地点 | 已有条件、缺地点提示、补充入口；旁注定位失败与手动补充的去向 |
| B-S03 条件齐全 | 地点／人数／预算／限制摘要，进入推荐的动作 |
| B-S04 修改条件 | 原值、应用、取消；修改后的旧结果与更新提示 |

可以用 2 张草图加状态批注表达这 4 个状态，不要求画 4 张高保真页面。

### 交什么、写到多细

在 B 模块补一张操作表，逐行写“用户做什么 → 页面怎样变 → 保留哪些信息 → 下一步去哪”。附上述画面或链接，写至少 3 条行为例子，列未定问题及建议。重点检查：缺地点不能推荐、信息齐全不重复问、取消修改保留原值。

给 C 的样例输出写清：原话、学校东门、一个人、30 元以内、仅本餐排除面食；预算来自本次输入还是已确认默认值。给 D 留默认值来源疑问，给 E 留补问和输入状态。

定位授权拒绝、多项缺失、含糊地点、超出单人范围、请求失败等，首轮先标注去向，后续补完整产品行为。技术实现问题单列，不负责验证定位接口。

## C 推荐与选定

**目标：让用户看懂推荐差别，分清查看与选定，并在不合适时继续选择。** 正式需求写在 [C 模块](./模块/C-推荐与选定.md)。

### 先看什么

在原型点三家卡片、地图点位、“换一组”“就这家”；读 PRD 第 3.1、4 节及 R-03、R-04、R-07、R-10，再看 C 模块。

### 具体补什么

按下面顺序动手：先列卡片字段，再画正常推荐，旁注候选不足；随后连出地图查看、换推荐和明确选定，最后写操作表。地图只表达点位和卡片关系，不需要先接地图服务或重画整套地图产品。

1. 主推荐与备选各显示哪些信息，默认展开什么，怎样比较三种角色。
2. 每张卡片的一句理由和两个标签依赖什么依据，价格或距离未知怎样显示。
3. 点地图怎样找到对应卡片，查看位置与明确选定怎样区分。
4. 换推荐保留什么条件；候选不足、重复、没有更多候选时怎样解释和继续。
5. 选定后显示什么，位置／外部导航入口在哪里，后续反馈怎样进入。

独立样例：学校东门、一个人、30 元以内、本餐不吃面食。家常饭 A 为 24 元／350 米，杂粮饭 B 为 28 元／550 米，粥铺 C 为 18 元／180 米。无需等待 B 或真实地图返回。

### 画哪些原型

| 编号 | 首轮必须表达的内容 |
| --- | --- |
| C-S01 推荐正常 | 主推荐展开、两个备选摘要、角色、理由、价格距离、操作入口 |
| C-S02 候选不足 | 只有两家时的布局；旁注无匹配与未知价格怎样提示 |
| C-S03 查看与调整 | 点位对应卡片、换一组、没有更多候选的提示和去向 |
| C-S04 明确选定 | 选定确认、位置入口、返回其他选择；不声称已经用餐或满意 |

可以画一张推荐页，旁边用小图或批注表达不足、更新和选定的变化。地图只需示意点位关系。

### 交什么、写到多细

在 C 模块交字段表、操作表、草图链接、至少 3 条行为例子及未定问题。字段表要有“名称、含义、期望来源、缺失时表现”；不设计接口或排序算法。

例子至少覆盖：只有两家不凑第三家、换推荐保留限制、打开地图不算选定。向 D 表达清楚“家常饭 A 这家店”和“家常饭这一类”的区别；向 E 提供必须显示的信息和状态。

真实地图接入、字段可得性和导航能力列为开发疑问；严格预算遇到未知价格时写自己的产品建议，交 A 汇总。后续补完整的无匹配、地图失败和条件变化后的等待／失败表现。

## D 反馈与个人偏好

**目标：让用户理解反馈影响什么、记住了什么，以及怎样纠正。** 正式需求写在 [D 模块](./模块/D-反馈与偏好.md)。

### 先看什么

走原型“当次反馈”和“偏好纠错”；读 PRD 第 3.2 节及 R-02、R-05、R-06、R-08、R-09、R-10。再读[编辑长期偏好的示范](./模板/需求填写示范-编辑长期偏好.md)和 D 模块。

### 具体补什么

按下面顺序动手：先用已有长期记录画个人页与编辑／取消，再补删除和结果状态；然后用共同样例写两条代表反馈路径，最后补标签规则表。对尚未确定的长期生效时机提出建议，其余部分继续推进。

1. 给已有八个反馈标签补对象、当次／长期范围、生效与提示、歧义及待定问题。先把“今天不想吃这个”和“这类以后别推荐”两条路径写完整。
2. 个人页分开显示日常默认值和长期记录；记录中展示对象、内容、范围和来源。
3. 编辑怎样进入、取消、保存成功或失败；删除怎样确认和取消；无记录怎样继续选餐。
4. 偏好变化后回首页保留什么，旧推荐怎样处理，何时提醒重新获取。

独立样例：已有长期记录“不推荐面食”，来源是曾明确反馈“这类以后别推荐”；当餐不额外排除面食，以便观察纠错影响。另用“家常饭 A／家常饭类别”模拟反馈。不等真实保存接口。

### 画哪些原型

| 编号 | 首轮必须表达的内容 |
| --- | --- |
| D-S01 列表 | 默认值、长期记录、范围来源、编辑与删除入口 |
| D-S02 编辑 | 原值、待保存内容、保存和取消 |
| D-S03 至 D-S05 | 保存中、成功、失败，可先在编辑图旁批注 |
| D-S06／D-S07 | 删除确认、取消、删除后的空状态 |
| D-S08 反馈 | 当前店或类别、标签、作用范围、结果提示 |

首轮用列表、编辑、反馈 3 张草图，加删除和结果状态批注即可；不要求每个编号画一张完整页面。

### 交什么、写到多细

交八标签规则表、两条代表反馈操作表、个人页流程、草图和至少 3 条行为例子；未定问题附建议。例子至少覆盖当次不长期化、取消编辑不改变原值、删除后不再用旧记录。

向 C 说明哪条偏好已成功生效、影响哪个对象；失败和待保存不当成有效变化。E 根据你的业务含义统一提示样式。

长期保存触发与记录归属尚有 Q-03、Q-08、Q-10 等问题，写用户可见规则建议交 A。身份、存储和保存机制另列开发疑问，不能把“长期范围”写成“已经立即保存”。后续补其余标签的完整分支和失败恢复。

## E 整体交互与视觉设计

**目标：把两页做成一致、清楚、能复用的手机界面。** 设计专业同学主责；正式说明与设计文件入口放在 [E 模块](./模块/E-交互与用户验证.md)。

### 先看什么

走原型三条路径；读 PRD 第 3、5、6、7.1、8.4 节及 E-03。先用当前 PRD 和灰度页开工，不等待 B/C/D 所有文案定稿。

### 具体补什么

先做 **E-S01 获得推荐后的首页**。用现有餐厅和条件样例提出一套视觉主方案，同时批注个人页与一处局部状态。先提交首轮成果，A 采用某个方向后，再将其扩展到完整个人页和公共规范。B/C/D 尚未交稿时，直接用现有字段与状态设计，未定文案标占位。

1. 首页先看什么，地图、主推荐、备选和对话怎样分配注意力；个人页怎样分组。
2. 提出一套配色与字体层级，并解释为何适合日常选餐；两页保持一致。
3. 统一按钮、输入框、卡片、标签、地图编号、提示与导航的表现。
4. 说明缺信息、等待、无匹配、失败、未保存、已生效等公共状态；不能只靠颜色表达。
5. 检查窄屏、键盘弹出、取消和返回，是否保留必要内容并有下一步。

首页样稿至少标明以下视觉元素，并说明主次关系：地图区、主推荐、备选卡片、对话入口、底部导航；正文／辅助文字／标题；主按钮、次按钮、选中和失败提示。A 与 E 判断能否读清信息、区分查看与选定、找到下一步，再采用配色和样式。E 负责交互与视觉判断，业务语义由各模块负责；E 不承担全部模块需求和共享原型代码。

### 画哪些原型

| 编号 | 首轮交付 | 后续补齐 |
| --- | --- | --- |
| E-S01 首页 | 一张推荐状态视觉样稿，表达地图／卡片／对话关系 | 关键公共状态与窄屏表现 |
| E-S02 个人页 | 在现有截图批注分组、层级、返回关系 | 一张完整个人页视觉稿 |
| E-S03 局部状态 | 一处反馈或编辑状态 | 与公共控件及成功／失败状态对应 |
| 公共规范 | 基础色、正文与标题层级、主要控件样式 | 一页完整公共控件与状态规范 |

设计专业同学负责布局和交互判断，也可提出结构优化。涉及流程、范围或反馈语义的改变，列建议交 A；未定业务内容可以先用明确占位。

### 交什么、写到多细

首轮交首页样稿、个人页批注、一处局部状态、视觉方向与基础规范，附至少 3 条检查场景和未定问题。设计文件可用团队熟悉的工具，链接放回 E 模块；在线文件注明交付版本／日期，并附关键画面 PNG 或 PDF 快照，具体按 [Git 约定](./Git协作约定-给AI.md)的图稿交付说明执行，不要求改 HTML。

自查首次选餐、当次反馈、偏好纠错能否讲通；检查 320 和 430 宽度、主次动作、查看与选定、当次与长期的区别。正文对比度至少 4.5:1，大字至少 3:1，点击区域按项目约定至少 44px。

首轮 E-01 与 E-03 主任务合计约 3 小时。E-03 完整视觉初估 4 小时，已含首轮视觉的 1.5 小时，后续约 2.5 小时补齐，不能再重复算一个 4 小时任务。用户试用为可选补充。

## A 统筹与异步交付

### A 接下来做什么

1. **会前准备和演示：** 打开现有原型，按会议提纲预走三条路径；会中介绍项目、演示 3–5 分钟，登记认领、实际可用时间、首稿日期和资料入口。
2. **接收模块稿：** 检查需求、图、至少 3 条行为例子及未定问题是否对应。优先核对条件字段、当次／长期范围、旧推荐失效、返回保留与保存提示；新方案和已有规则冲突时，记录具体场景并作取舍。
3. **确定阶段视觉方向：** 与 E 核对首页样稿的区域主次、文字与动作层级、控件及配色，把采用方向和待改项写入[决策记录](./决策记录.md)。可以书面完成，不要求全员先开评审会。
4. **整合可点击原型：** 和 AI 继续维护 `协作区/原型/eatwhat-flow.fragment.html`，逐项接入采用的业务交互和视觉；同步导出 index.html，并检查改动影响的按钮、状态和三条主路径。其他分支可以暂用明确编号草图说明，记录尚未做成可点击状态的部分。
5. **更新产品交付：** 分批整合 [PRD](../PRD.md)，同步模块和画面引用、看板与未定问题。给开发组的资料包括整合 PRD、模块细节、可点击原型、采用的视觉规范及技术疑问；开发组自行确定实现方式与排期。

A 保留共享 PRD、决策记录和原型源的统一维护权；B/C/D 提供业务草图，E 提供公共视觉。已有框架不要求重写，模块不必全部齐交才开始整合。AI 可以辅助对照文档、实现样例交互和检查，但采用哪种方案由 A 及对应负责人作出判断。

后续整合按收到的稿件分批做，计入 A 本人每周 4–6 小时，不把全部原型实现叠加到其他成员的首轮粗稿预算。实际工时和下一步由 A 在原看板记录。

### 异步怎样配合

1. **各自开工：** 用 PRD 第 7.1 节样例，先完成自己的文字、图和案例。不要把产品运行时 B → C → D 的信息流当成写文档的先后顺序。
2. **有缺口就注明：** 写“临时假设、缺什么、自己的建议、影响谁”，继续做其他部分。共享规则交 A 取舍；普通文案和控件由自己推进。
3. **提交四样：** 需求说明、草图或设计稿、至少 3 条行为例子、待定问题（无则写暂无）。自查后直接交 A，互评不设门槛。
4. **A 分批汇总：** Git 模式由 A 更新共享看板和决策记录，成员在提交说明报进展。其他模块的细节后续变化时，主责再回填受影响部分。

“写清楚”至少达到这个程度：点击编辑看到原值；取消保留原值；保存成功显示新值；失败保留本次修改并能重试。只写“支持编辑、优化体验”还不够。案例描述预期行为，不需要执行真实接口。

### 平时怎样向大家同步

有实际推进时，在自己的工作时段结束后发三项：本次补了什么及成果链接、下一步做什么、需要 A 决定什么（附建议和影响，无则写无）。不要求每天上线或即时回复，也不额外安排一份日报。

A 有变化再向相关成员发摘要：已经采用的改动与入口、需要谁处理的具体问题、交稿时间是否变化。状态和决定分别回到原看板与决策记录，不只留在群消息中。真实用户试用仍为可选，未经实际开展不能写成已验证。

### Git 与 AI 怎么配合

每人使用自己的任务分支，只修改自己的模块与草图；A 统一合并到 main。AI 先读 [Git 协作约定](./Git协作约定-给AI.md)和根目录 AGENTS.md，再执行具体任务。共享原型不要多人同时直接修改。

不会 Git 的同学可把以下内容发给自己的 AI；仍无法使用仓库时，交模块改稿和图片，由 A 汇入。PDF 是分享快照，正文仍维护在原模块，避免产生两份需求主稿。

```text
我负责 EatWhat 的【B/C/D/E】，本轮任务是【任务编号】。
先读 AGENTS.md、README、Git 协作约定、PRD 相关条目和我的模块。
按本分工说明补我的需求、草图说明、行为例子及待定问题。
操作表写清当前状态、按钮可用条件、下一状态、信息保留及取消／失败后的去向。
我是 B/C/D 时先画业务草图；我是 E 时先交一张首页视觉样稿、个人页批注和局部状态。
使用共同样例，不等待其他成员；只修改我的模块及自己的草图。
先报告仓库状态与将修改的文件，再按当前授权执行；不替我确认未定取舍。
```
